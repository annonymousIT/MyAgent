# ADR-0030 保存の捏造ガード＋相対日付の解決（記憶を取りこぼさない）

- 状態: 採用（2026-06-11）。ADR-0029（永続記憶）の信頼性ハードニング。

## 課題
脳=haiku が、記憶・予定の保存依頼に対して **ツールを呼ばずに「登録しました」「覚えました」と返す**ことが頻発（実測: 「毎週火曜ゼミ」3/4・「〜覚えといて」2/3 で未保存のまま完了を断定）。
記憶が売りの相棒で記憶を黙って取りこぼす＝致命的な穴。加えて **相対日付（来週の月曜）を haiku が自分で計算して誤る**（来週月曜=6/15 を 6/16/6/22 と誤登録）。

## 判断（3層で塞ぐ）
1. **鉄則プロンプト（最優先）**: システムプロンプト先頭に「保存依頼は必ず add_schedule/remember を呼ぶ。呼ばずに『登録/記憶しました』と言うのは禁止」を置く。→ 予定の捕捉が 1/4→4/5 に改善（記憶は 1/3 で不足）。
2. **確定的ガード（core.run_turn）**: 返答が保存"完了"の断定（『〜しました』『登録完了』等の完了形フレーズ）を含むのに保存ツールを呼んでいなければ、`tool_choice:{type:any}` でツールを強制し、本当に保存させてからその結果を返答にする。プロンプトの確率に頼らず Python が担保。完了形フレーズだけに反応させ「記憶に無い」等の読み取り応答では誤発火しない（実機で確認）。
3. **相対日付を Python が解決**: ①日付早見表を「今週/来週/再来週＋曜日ラベル」で注入（haiku は計算でなく語彙で引く）。②`add_schedule(weekday, once=true)` で「来週の◯曜」は実日付を Python が算出（LLM に日付計算させない）。

## 影響
- core.py: `_RULES`（鉄則）を build_system_prompt 先頭に。`_SAVE_TOOLS`/`_SAVE_CLAIMS` と `_force_save` を run_turn に追加（dry_run は対象外＝検証用モード）。
- profile_store.py: 日付早見表を週ラベル化。add_schedule に `once`（その曜日に1回だけ→次の該当日を算出）。
- tools.py: add_schedule に `once` 引数＋説明更新。
- 検証(2026-06-11・実モード): 保存依頼5件すべて profile.json に実保存、読み取り「来月の予定」は誤発火せず正直に「記憶に無い」、想起も成功。「来週の月曜」→6/15(月) 正解。

## 残る制約
- haiku の確率挙動自体は消えない（鉄則＋ガードで実害＝データ消失を防ぐ二段構え）。tool_choice 強制時に稀に別ツールを選ぶ可能性は理論上残る（文脈で抑制）。
- facts 肥大時の注入トークン増・要約圧縮は将来（[ADR-0029] と同じ）。
